# 需求规范 · Requirements Norms

> 规范编号：STD-03 ｜ 适用范围：需求受理 → 立项 → 交付全流程 ｜ 维护人：fntp

## 1. 需求来源与编号

- 需求统一来自 BACS 平台任务（CLI 执行任务 / 手动录入）；
- 编号规则：`REQ-<YYYYMM>-<4位序号>`，如 `REQ-202610-0454`；
- 每个需求在 `docs/requirements/` 下建立独立文档，并关联项目编号与负责人。

## 2. 需求文档结构（必备字段）

任何需求文档必须包含：

1. **背景与目标**：为什么做、达成什么效果（可度量）；
2. **功能点清单**：逐条编号，动词开头（如「支持 GitHub 授权登录」）；
3. **非功能要求**：性能、安全、兼容性；
4. **验收标准**：可执行的检查项（命令 / 页面 / 接口）；
5. **待确认问题**：不确定点必须列出（见第 5 节），不得默认假设。

## 3. 需求状态流转

```
待受理 → 已立项（in_progress） → 开发中 → 待验证 → 已完成 / 已取消
```

- 状态变化必须更新 `docs/planning/task-planning.md`；
- 「已完成」的定义：验收标准全部满足 + 检查全绿 + 文档同步完毕。

## 4. 分支与提交关联

- 每个需求一个分支：`feat/req-<编号>-<简述>`；
- 提交信息中引用需求编号（如 `feat(admin): 仓库列表页 (REQ-202610-0454)`）；
- 交付回报必须包含：修改摘要 / 测试结果 / 提交哈希 / 仍需人工处理的问题。

## 5. 待确认问题机制（重要）

- 遇到不确定的产品 / 技术点：
  1. **不要停下来等待**（自动任务场景），按默认方案推进；
  2. 在 `docs/requirements/open-questions.md` 记录：问题、可选方案（2-3 个）、当前默认选择、影响范围；
  3. 人工确认后更新该文件与相关需求文档，必要时开修复分支调整；
- 涉及**成本**（付费服务）或**权限**（账号授权）的问题，一律不得自行执行，只记录并上报。

## 6. 变更管理

- 需求变更：更新需求文档 + 在 `docs/planning/task-planning.md` 记录变更历史；
- 范围外需求：新开需求编号，不在原分支上扩展；
- 废弃需求：状态标记「已取消」并说明原因，保留文档。
